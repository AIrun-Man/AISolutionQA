# Quality Engineering Workflow Orchestration

## Inputs

One of:

- Jira story key or URL
- Requirement document path
- Pull Request URL or owner/repository/number

Required integrations: Devin's connected Atlassian MCP when Jira is involved and connected GitHub MCP for repository, branch, PR, commit discovery, and source acquisition. Reuse the authenticated GitHub Enterprise integration for PR publication and Actions only when its existing tools support the operation. Inspect actual MCP tool schemas; never assume methods or fields.

## Instructions

First load and validate repository-root `governance-config.json` with `loadGovernanceConfig`; there are no code-level governance threshold fallbacks. Create and validate a plan with `createQualityWorkflowPlan(sourceType)` and `validateQualityWorkflowPlan(plan)`. Execute stages in dependency order, recording conditional stages as skipped with a reason when their condition is false. Retain stable IDs and evidence at every stage:

For Jira generation, first load and validate `generation-config.json`, resolve paths with `resolveJiraGenerationPaths`, and call `createJiraGenerationLayout`. All outputs, reports, and execution artifacts must be written beneath the configured `outputFolder/<JIRA-ID>`; never use a hardcoded report or generated-output location. Honor generation flags before selecting/generating UI, API, or performance scripts.

Before building unified evidence or generating tests, establish implementation lineage first. For Jira, use `repositoryContext.branchExists`: acquire the exact story-associated branch when present; when confirmed absent, run Merge Traceability in this priority order: linked PR, merge commit, story-linked commit history, then repository diff. Consult `memory.md` references as discovery leads, verify them against authorized repository evidence, evaluate Implementation Trust, and run Commit Reconstruction only after trust passes. Do not treat `not_checked` or `unknown` as branch absence. Persist `implementation-source-model.json`, `implementation-trust-report.json`, and, when reconstructed, `implementation-reconstruction-model.json` under the configured Jira output folder using their platform schemas.

After implementation analysis, run Existing Test Intelligence before any test-case or automation generation. Load configured UI/API repository references from `generation-config.json`; discover and acquire them only through the authorized GitHub integration and only when required. In order, build the Automation Repository Model, Framework Intelligence Model, Repository Standards Model, Pipeline Execution Model, Test/Automation/Suite Inventories, Coverage Discovery Model, Regression Impact Model, Coverage Delta Model, and Reuse/Generation Strategy. Analyze GitHub Actions workflows but do not dispatch them during discovery. Then run API Intelligence before ADR discovery and unified evidence correlation, followed by application discovery, Xray repository analysis, environment discovery, and test-data analysis. Persist the complete bundle with `writeExistingTestIntelligenceForJiraStory` and the existing application, Xray, test-reuse, environment, and test-data artifacts under the configured Jira output folder. Validate the bundle against `platform-core/schemas/existing-test-intelligence.schema.json`. Unknown or unavailable repository evidence must remain visible and cannot be reported as a completed reuse check.

1. **Acquire story and source context.** For Jira, follow `jira-story-processing.md` using connected Atlassian and GitHub MCP integrations. Populate `context.repositoryContext` with branch, PR, merge-commit, commit-history, and reconstruction facts. If the story branch is absent, use `discoverImplementationSources` with linked Jira/GitHub evidence and read-only memory leads; do not use an unlinked default branch. For a document, preserve source references. For a PR, inspect its metadata, diff, and changed paths. Record repository and immutable revision references.
2. **Govern requirements before analysis.** Follow `requirement-governance.md` and call `validateRequirementsBeforeAnalysis` on the raw story key/summary/description, Acceptance Criteria, and available business-rule/context/dependency data. Block `analyzeRequirements` when the governance report fails; preserve unresolved ambiguity, missing Acceptance Criteria, duplicates, conflicts, dependencies, and business-context gaps for owner resolution.
3. **Understand requirements.** Reuse Prompt 16 outputs and `analyzeRequirements` with the requirement-analysis schema only after requirement governance passes. Preserve requirement and acceptance-criterion wording; never resolve ambiguity by inference.
4. **Analyze implementation and map traceability.** On the direct path, retrieve the exact story-associated branch revision. On the missing-branch path, require a passing result from `evaluateImplementationTrust`, then create an `Implementation Reconstruction Model` with `buildImplementationReconstructionModel` from verified PR/merge/commit/diff evidence. Never reconstruct from memory references alone. Analyze added, modified, and deleted files, business logic, services, validations, error handling, APIs, data interactions, and UI behavior. Use `validateRequirementsAgainstCode` and `analyzeSourceImpact`, create stable Requirement-to-Code mappings, and persist them with `writeRequirementCodeMappingsForJiraStory` and the mapping schema. Surface unmapped files and limitations.
5. **Correlate evidence, assess risk, and design tests.** Run API Intelligence and ADR discovery before this stage. Call `correlateEvidence` with the current Requirement Analysis, historical Jira context, Implementation Source Model, optional trusted Reconstruction Model and Implementation Trust report, exact implementation mappings/findings, explicit semantic confirmation IDs for mappings verified against the changed source, API contracts and mappings, ADR evidence, UI discovery, Xray repository/reuse, Existing Test Intelligence models, environment, test-data models, and source references. Source lineage is global provenance; it does not by itself confirm an Acceptance Criterion. Lexical matching alone is never confirmation. Persist `unified-evidence-model.json` using `writeUnifiedEvidenceForJiraStory`. Generate scenarios from validated requirements and call `generateTestCases(analysis, implementationMappings, evidenceModel, reuseAnalysis, testDataModel)` so exact reusable scenarios are omitted and evidence/data-set IDs remain linked. Partial reuse must yield extension recommendations, not be misreported as full coverage. Before proposing new tests, consult memory for historical stories, Xray tests, and coverage; use only exact, explicitly linked matches. The engine must reject incomplete mappings. Never generate tests from requirements alone. Use historical stories, defects, executions, failure classifications, and coverage gaps to prioritize test risk without inventing behavior.
6. **Govern missing test candidates.** Require a passing Reuse Governance Report before generation. Call `validateGeneratedTests` and follow `jira-test-case-creation.md` and `xray-import.md`. Use Coverage Delta and Reuse Strategy to skip covered targets, link reusable automation, and extend partial matches only when supported. Do not create or import remote cases at this stage; use configured destinations and preserve data-set IDs/references.
7. **Review coverage, then create only missing Xray tests.** Follow `coverage-intelligence.md` with requirements, acceptance criteria, implementation findings, Coverage Discovery/Delta, reuse decisions, generated cases, risk evidence, and traceability. Resolve blocking requirement/test-design gaps and persist the review decision before creating Xray import artifacts or remote issues. Only after coverage review, Reuse Governance, and Test Governance pass, generate canonical `xray-import.json` for missing cases only, derive CSV only from that JSON when requested, and import only when `xrayAutoImport` is enabled and the existing integration supports the discovered tool schema. Persist returned Xray IDs/URLs; never report remote issue creation without a successful integration result.
8. **Run API Intelligence before ADR discovery and evidence correlation.** When API candidates exist, follow `api-intelligence.md`: discover APIs through authorized oneAPI, Swagger, OpenAPI, ReDoc, documentation, or repository contracts; normalize operations; correlate requirements and Acceptance Criteria to contracts; map operations to the exact approved branch or trusted reconstructed PR/commit source; score API risk; calculate endpoint/method/request/response/validation/error/security coverage; and design API/Xray cases. Apply API governance from the central config. Then discover ADRs as supporting evidence before evidence correlation. Use the connected Atlassian MCP for Xray only after inspecting its actual tool schema. Stop API script generation when applicable thresholds fail.
9. **Select automation strategy and generate.** Build requirement/surface evidence from the analyzed code and call `selectAutomationStrategies`. Use `validatePerformancePlan` before performance generation, honoring configured user/duration/ramp/request/size/concurrency/environment limits. Choose UI, API, contract, component, or performance automation from requirement type and affected code, then honor the matching generation flag. For API scripts, consume the API automation plan and Xray case links, and reuse the existing `HttpClient`, `RequestBuilder`, endpoint definitions, named environments, Zod schemas, `validateResponse`, and API reporting. Contract tests use existing API contracts/validators. Generate component or performance automation only when an approved runner is already configured; do not add or replace frameworks. Generate only approved cases and automation targets explicitly marked missing by Reuse Strategy; never regenerate existing automation. Run `validateAutomationScripts`, `detectHallucinations`, and `validateDataPrivacy` on all generated assets; persist only sanitized artifacts and block staging when any required report fails.
10. **Select regression scope and draft suites.** Use `analyzeRegressionImpact`, `buildSmartRegressionRecommendation`, and `selectTests` with changed files/APIs/components, coverage delta, the existing test inventory, suite inventory, and explicit environment/PI/ART context when supplied. Draft smoke, functional, regression, API, and performance selections. If source changes are unmapped, select full regression. Record selected/excluded tests and reasons.
11. **Build final coverage intelligence.** After test and automation mappings exist, call `analyzeCoverageIntelligence` with code paths derived from the exact PR/commit diff and evidence-based requirement mappings. Set `xrayEnabled` from the configured management tool and provide only returned Xray issue links; set `scriptCoverageEnabled` when automation is in scope and provide concrete generated script paths. Produce requirement, implementation, API, Xray, and script coverage; missing requirements/tests/Xray links/scripts/implementations; risk recommendations; and coverage percentages. Compare with prior coverage snapshots when available.
12. **Calculate readiness and run the Enterprise Quality Gate.** Derive `CoverageGovernancePolicy` with `coveragePolicyFromGovernance` and API thresholds with `apiPolicyFromGovernance` from `governanceConfig.qualityGates`; never use code-level threshold defaults. When reconstruction is required, include the Implementation Trust report and configured `qualityGates.implementationTrust` policy; a missing report/policy, failed mapping/lineage check, or below-threshold score blocks readiness. Call `calculateStoryReadiness` with the configured `minimumReadinessScore`, persist its report, then call `evaluateEnterpriseQualityGate` with requirement/test/script/performance/hallucination/privacy/coverage/readiness reports, trust evidence when applicable, and duplicate/security counts. Persist `execution-readiness-report.json` conforming to `platform-core/schemas/execution-readiness.schema.json`. Call `assertExecutionReady`; BLOCK stops all subsequent side effects, and WARNING proceeds only if config permits it. Finalize the Execution Recommendation from the governed suite selection and discovered pipeline, preserving explicit INT and REX/RAM Program Increment context.
13. **Publish generated automation.** Only after `assertExecutionReady` passes, create a scoped branch, commit only governance-passing sanitized scripts using repository standards, and create a draft PR using `.github/pull_request_template.md`. Do not include secrets, reports, blocked artifacts, or unrelated files. Never merge or change protected branches.
14. **Link automation to Jira test cases.** For Jira sources, link each generated script, repository branch, commit, and PR to the corresponding stable Jira test-case issue. Persist returned Jira keys/URLs and trace links; do not guess tool fields or report failed link operations as successful.
15. **Validate and execute GitHub Actions.** Compare the Execution Recommendation with the discovered Pipeline Execution Model and validate repository/workflow compatibility first. Only after compatibility checks pass, `assertExecutionReady` passes, and the draft PR exists, use the existing authorized GitHub Enterprise integration to dispatch and monitor the configured PR validation workflow. Use configured workflow/repository identifiers; do not hardcode a hostname or claim a run without a returned run ID and result. If dispatch or access is unavailable, report the blocker; never imply a workflow ran.
16. **Analyze results and maintain tests.** Collect run/job IDs, artifacts, and sanitized failures. Use `analyzeFailure`; keep ambiguous results `undetermined`. Run `analyzeTestMaintenance` against supplied execution history and locator metadata. Product-defect creation requires explicit evidence and human review.
17. **Promote and update Jira/Xray.** Mark automation/PR ready only when the Enterprise Quality Gate and required Actions checks pass and approvals are present. Follow `jira-defect-sync.md`; search for duplicate defects, create only supported product defects after required review, and synchronize execution status, coverage, automation links, results, traceability, and Xray executions when `updateXrayExecution` is enabled and the existing integration supports it. Report permission failures without claiming success.
18. **Report and preserve read-only memory.** Use the existing reporting layer to persist each governance report, source/reconstruction/trust models, coverage/traceability outputs, execution results, and executive summary under the configured Jira folder. Make verified artifacts available as read-only memory references; do not add automatic learning, memory updates, or synchronization. Do not commit reports or privacy-blocked artifacts.

## Universal gates

- Never invent requirements, test evidence, or successful results.
- Stop when a required integration, permission, source, or validation gate is missing.
- Do not merge PRs or change protected branches automatically.
- Keep credentials in Devin's approved MCP/secrets configuration; never write them to files or logs.
- Preserve the existing architecture and request human approval for requirement interpretation, test-case approval, defect creation, unresolved risk, and PR review/merge.

## Output

Return a stage-by-stage status table with stable IDs, exact commands, run URLs, artifacts, issues created/updated, blockers, and residual risks.
